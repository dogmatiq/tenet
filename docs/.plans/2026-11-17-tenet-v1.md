# tenet v1

## Context

tenet is a Go library that reverses connections. It lets a server that can only make outbound connections accept
connections from a client: the server connects to the client over a secure WebSocket, and the client then dials
connections back to the server through it. It has nothing specific to any application or protocol.

Its first users are servers that run in networks that allow only outbound connections, yet must serve gRPC to tools
outside those networks.

## Terms

- **Initiator**: the process that connects to the acceptor over a secure WebSocket.
- **Acceptor**: the process that accepts the initiator's WebSocket.
- **Dialer**: the side that dials connections through the WebSocket. The acceptor is always the dialer.
- **Listener**: the side that accepts those connections. The initiator is always the listener.
- **Tunnel**: one WebSocket, and the connections that it carries.

"Connect" is used only for the WebSocket, and "dial" only for the connections inside it.

## Decisions

### What tenet is
- A Go library, `dogmatiq/tenet`. Its README starts: "tenet lets a server that can only make outbound connections accept
  TCP-style connections from a client, by connecting to the client over a secure WebSocket."
- It carries reliable, ordered byte streams only, like TCP. It has no datagrams.
- It mentions no protocol that runs over it, and depends on no gRPC library. gRPC is only its main use.
- Many connections share one WebSocket, multiplexed with yamux (`github.com/hashicorp/yamux`). yamux is an
  implementation detail: nothing in tenet's API or documentation names it.

### Transport
- The outer connection is a secure WebSocket only. The acceptor serves it itself, or behind an HTTPS proxy that
  terminates TLS with its own certificate, such as the edge of a hosting platform that accepts only HTTPS. Raw TLS and
  SSH are not used: a WebSocket covers every deployment that they would, and it passes through the HTTP proxies of
  networks that allow only outbound connections.

### The initiator's side
- The initiator gets a `net.Listener`. Any server that accepts connections can serve it, such as `grpc.Server.Serve`.
- It connects with an `http.Client` and request headers that its application gives it, so redirects, proxies and TLS
  follow that client, as for any other HTTP request. tenet adds no rules of its own.
- It connects again whenever its WebSocket ends, with backoff that its application chooses.

### The acceptor's side
- The acceptor admits each initiator in its own HTTP handler, with whatever checks it uses for other requests, such as
  a token, basic auth, or mutual TLS where it terminates TLS itself. The handler then passes the request to tenet's
  `Accept`, which upgrades it and returns a `Dialer`, the dialer's side of the tunnel, in the same function. The
  `Dialer` doesn't depend on the request's context, so it lives on after the handler returns.
- The `Dialer`'s `Dial(ctx)` opens a new `net.Conn` to the listener over the same WebSocket. With gRPC, it is passed to
  `grpc.WithContextDialer`, and grpc-go's own reconnects and retries work as designed while the WebSocket lives.
- The `Dialer`'s `Done()` signals that the WebSocket has ended, and its `Close()` ends it.

### Liveness and bounds
- Each side has two settings, both about liveness: an interval, which is how often it checks that the other side still
  answers, and a timeout, which is how long a check or a write may stall before the tunnel ends. They play the part of
  TCP keepalive, so a silent break ends the WebSocket on whichever side notices first.
- Everything else is fixed and documented as bounds, as the kernel's settings are for TCP: at most 256 connections
  waiting for the listener to accept them, and at most 256 KB buffered per connection in each direction. A connection
  beyond the listener's backlog is reset, as TCP resets one beyond its own backlog.

### Limits
- tenet adds no limits on connections, and no timeout on dialing one. The listener limits what it accepts, and the
  dialer what it dials, as they would without a tunnel.
- A dead initiator is noticed by the liveness check, and a listener that stops accepting leaves the dialer to its own
  context and deadlines, as a TCP backlog does.
- `Dial` returns as soon as its context ends, and a cancelled dial leaves nothing waiting behind it, so a dialer that
  keeps retrying against a listener that never accepts can't pile up work inside the tunnel.

### Ending
- Closing the initiator's listener behaves like closing any `net.Listener`: no new connections open, and the dialer's
  new dials fail at once, while existing connections are left to the application. The WebSocket ends after the last one
  closes. Grace and its deadline come from the server on top, such as `grpc.Server.GracefulStop`.
- Cancelling the initiator's context ends the WebSocket and every connection at once.
- When a WebSocket ends, every connection on it ends, pending dials fail, and later dials fail.
- Why a tunnel ended is reported as an error on both sides: from the acceptor's `Dialer`, and to the initiator's
  backoff function, which is also told why an attempt to connect failed. The listener's `Accept` doesn't report it,
  because the listener outlives each WebSocket, and an error from `Accept` would stop the server that serves it. tenet
  doesn't log, just as Go's `net` package doesn't.

### Identity
- tenet doesn't know who connected, or which WebSocket replaces which. Each acceptor works that out from what it learns
  over the connections, such as the server's certificate, or what the server reports about itself.

## Open
- The names of the liveness settings and of the backoff function. The names of the entry points are settled in
  [the API plan](2026-11-17-tenet-v1-api.md#decisions).
- The path of the WebSocket, and whether it names a subprotocol.
- Whether tenet can tell when the other side has acknowledged a new connection, which it needs in order to count pending
  dials so that a cancelled dial leaves nothing waiting behind it.
