# tenet v1

## Context

tenet is a Go library that reverses connections. One program connects to another over a WebSocket, and that
program then opens connections back through the WebSocket, as if it could connect directly. It has nothing specific to
any application or protocol.

Its first users are programs that run in networks that allow only outbound connections, yet must serve gRPC to tools
outside those networks.

## Terms

- **Client**: the program that calls `Connect`. It connects to the server over a WebSocket, and accepts the
  connections that the server opens, from the `Listener` values that `Client.Listen` returns.
- **Server**: the program whose `http.Handler` passes the client's request to `Accept`. It opens connections to the
  client, with the `Dialer` that `Accept` returns.
- **Tunnel**: the WebSocket between a client and a server. Connections pass through it.
- **Connection**: each stream through a tunnel. Its two ends are named by the types that hold them: the `Dialer`'s end
  and the `Listener`'s end.

"Connect" is used only for the WebSocket, and "dial" only for the connections inside it. "Client" and "server" mean
only the two ends of the WebSocket. A server for a protocol that runs over connections, such as `grpc.Server`, is
named with that protocol. [The API plan](2026-11-17-tenet-v1-api.md#terms) says how the doc comments use these terms.

## Decisions

### What tenet is
- A Go library, `dogmatiq/tenet`. Its README starts: "Tenet reverses the direction of TCP-style connections. One
  program connects to another over a WebSocket, and that program then opens connections back through the
  WebSocket, as if it could connect directly."
- It carries reliable, ordered byte streams only, like TCP. It has no datagrams.
- It mentions no protocol that runs over it, and depends on no gRPC library. gRPC is only its main use.
- Many connections share one WebSocket, multiplexed with yamux (`github.com/hashicorp/yamux`). yamux is an
  implementation detail: nothing in tenet's API or documentation names it.

### Transport
- The tunnel is a WebSocket, which is secure when the URL's scheme is `wss`. `Connect` also accepts `ws`,
  for use where TLS is not needed, such as in tests. The server serves it itself, or behind an HTTPS proxy that
  terminates TLS with its own certificate, such as the edge of a hosting platform that accepts only HTTPS.

- The WebSocket names a versioned subprotocol, such as `tenet.v1`, in its `Sec-WebSocket-Protocol` header. `Connect`
  sends it, and `Accept` confirms it or refuses the upgrade, so that a later change to the wire format is negotiated
  instead of breaking older peers. Only tenet's own code takes part, so whatever serves a `Listener` never sees it.
  `Accept` checks the header itself before it upgrades, because the WebSocket library negotiates no subprotocol for a
  client that names none, and a mismatch needs an HTTP error response, which can't be written after the upgrade.
  That response is 400 Bad Request, and its body names the subprotocol that the client must offer. `Connect` also
  refuses a WebSocket that the server accepts without choosing the subprotocol.
- The tunnel's bytes travel in binary WebSocket messages. Each end reads the messages as one continuous stream of
  bytes, so where one message ends and the next begins means nothing, and a yamux frame may span several messages. A
  text message ends the tunnel. This is part of the `tenet.v1` wire format.

### Libraries
- The WebSocket is made with `github.com/coder/websocket`. Its `DialOptions` take the `http.Client` that
  `WithHTTPClient` sets, the headers that `WithHeader` sets, and the subprotocol, and honor the client's redirect
  settings. Its `NetConn` turns the WebSocket into the byte stream that yamux needs. `github.com/gorilla/websocket`'s
  `Dialer` takes proxy and TLS settings instead of an `http.Client`, so it couldn't keep the promise of
  `WithHTTPClient`.
- yamux's `Config` is set as follows. The keepalive interval and `ConnectionWriteTimeout` are the values of
  `WithKeepAliveInterval` and `WithKeepAliveTimeout`, which default to 15 and 10 seconds, so the default interval is not
  yamux's 30 seconds. `MaxStreamWindowSize` keeps its default of 256 KB, which is the buffer bound. `Logger` discards,
  because yamux writes to standard error by default. `StreamOpenTimeout` is 0, because its default of 75 seconds closes
  the whole session when a stream isn't acknowledged in time, and tenet adds no timeout on dialing. yamux's
  `OpenStream` takes no context, so `DialContext` stops waiting when `ctx` ends, and resets the stream.

### The client's side
- `Connect` returns a `Client`, which keeps a tunnel open to the server. `Client.Listen` returns a `Listener`, which is
  a `net.Listener`, for each network and address. Any protocol's server that accepts connections can serve it, such as
  `grpc.Server.Serve`.
- It connects with an `http.Client` and request headers that its application gives it, so redirects, proxies and TLS
  follow that client, as for any other HTTP request. tenet adds no rules of its own.
- It connects again whenever its WebSocket ends, with a backoff policy that its application chooses.
- It tells its application each time a tunnel opens, ends or fails to open, through an observer.

### The server's side
- The server admits each client in its own HTTP handler, with whatever checks it uses for other requests, such as a
  token, basic auth, or mutual TLS where it terminates TLS itself. The handler then passes the request to tenet's
  `Accept`, which upgrades it and returns a `Dialer`, the server's half of the tunnel, in the same function. The
  `Dialer` doesn't depend on the request's context, so it lives on after the handler returns.
- `Accept` keeps the WebSocket library's check of the `Origin` header. It refuses, with 403 Forbidden, a request whose
  `Origin` names a host other than the request's own, so that a web page can't open a tunnel with a visitor's cookies.
- The `Dialer`'s `DialContext(ctx, network, address)` opens a new `net.Conn` to the client's `Listener` for that
  network and address, over the same WebSocket. With gRPC, it is passed to `grpc.WithContextDialer`, and grpc-go's own
  reconnects and retries work as designed while the WebSocket lives.
- The `Dialer`'s `Done()` signals that the WebSocket has ended, and its `Close()` ends it.

### Dialing
- A dial is answered by the client. `DialContext` opens a new stream through the WebSocket, sends the network and
  address, and returns when the client answers: the connection is queued on the `Listener` for that pair, or it is
  refused with `syscall.ECONNREFUSED` because no `Listener` has that pair. Because the dialer knows whether the client
  has the stream, a dial whose `ctx` ends first resets the stream, so that it leaves nothing waiting behind it.
- The client reads each new stream's address as soon as the stream opens, and queues or refuses the stream without
  waiting for any `Listener`. A `Listener` that never accepts therefore delays no other `Listener`.
- The dialer writes the network and the address first on the new stream, each as a two-byte big-endian length followed
  by its bytes. The client answers with one byte: 0 for accepted, 1 for refused and 2 for a full backlog. Every later
  byte belongs to the connection. A header that breaks the limits resets the stream. The version of this format is the
  subprotocol's. The Connections task writes it in a doc comment beside the code that reads and writes it.
- Each `Listener` has its own backlog of 256 connections, a queue of tenet's own, because yamux's `AcceptBacklog` counts
  every stream that waits on the session. A dial to a `Listener` whose backlog is full returns an error
  that wraps `syscall.ECONNRESET`.

### Liveness and bounds
- Each end has two settings, both about liveness: an interval, which is how often it checks that the other end still
  answers, and a timeout, which is how long a check or a write may stall before the tunnel ends. A silent break
  therefore ends the WebSocket on whichever end notices first.
- Everything else is fixed and documented as bounds: at most 256 connections
  waiting for a `Listener` to accept them, and at most 256 KB buffered per connection in each direction. A connection
  beyond the backlog is reset, as TCP resets one beyond its own backlog. A network is at most 64 bytes and an address
  at most 448, and `Client.Listen` and `DialContext` return an error that wraps `syscall.EINVAL` for a longer one.

### Limits
- tenet adds no limits on connections, and no timeout on dialing one. A `Listener` limits what it accepts, and the
  `Dialer` what it dials, as they would without a tunnel.
- A dead client is noticed by the liveness check, and a `Listener` that stops accepting leaves the `Dialer` to its own
  context and deadlines, as a TCP backlog does.
- `DialContext` returns as soon as its context ends, and a cancelled dial leaves nothing waiting behind it, so a
  `Dialer` that keeps retrying against a `Listener` that never accepts can't pile up work inside the tunnel.

### Ending
- Closing a `Listener` stops only its network and address: connections that wait in its backlog are closed, later dials
  to it are refused, and connections that `Accept` has returned are left to the application. Closing the `Client` stops
  it from connecting again and closes each `Listener`, and the WebSocket ends after the last connection closes. Grace
  and its deadline come from the protocol's server on top, such as `grpc.Server.GracefulStop`.
- Closing the `Dialer` ends the WebSocket and every connection immediately.
- When a WebSocket ends, every connection on it ends, pending dials fail, and later dials fail.
- Why a tunnel ended is reported as an error on both sides: from the server's `Dialer`, and to the client's observer,
  which is also told why an attempt to connect failed. `Listener.Accept` doesn't report it, because the `Listener`
  outlives each WebSocket, and an error from `Accept` would stop the protocol's server that serves it. tenet doesn't
  log, just as Go's `net` package doesn't.

### Identity
- tenet doesn't know who connected, or which WebSocket replaces which. Each server works that out from what it learns
  over the connections, such as the certificate that the protocol's server presents, or what that server reports about
  itself.
