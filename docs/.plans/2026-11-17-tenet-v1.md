# tenet v1

## Context

tenet is a Go library that reverses connections. One program connects to another over a secure WebSocket, and that
program then opens connections back through the WebSocket, as if it could connect directly. It has nothing specific to
any application or protocol.

Its first users are programs that run in networks that allow only outbound connections, yet must serve gRPC to tools
outside those networks.

## Terms

- **Client**: the program that calls `Connect`. It connects to the server over a secure WebSocket, and accepts the
  connections that the server opens, from the `Listener` values that `Client.Listen` returns.
- **Server**: the program whose `http.Handler` passes the client's request to `Accept`. It opens connections to the
  client, with the `Dialer` that `Accept` returns.
- **Tunnel**: the WebSocket between a client and a server. Connections pass through it.
- **Connection**: each stream through a tunnel. Its two ends are named by the types that hold them: the `Dialer`'s end
  and the `Listener`'s end.

"Connect" is used only for the WebSocket, and "dial" only for the connections inside it. "Client" and "server" mean
only the two ends of the WebSocket. A server for a protocol that runs over connections, such as `grpc.Server`, is
named with that protocol. [The API plan](2026-11-17-tenet-v1-api.md#terms) says how the doc comments use these terms.

## Decisions

### What tenet is
- A Go library, `dogmatiq/tenet`. Its README starts: "Tenet reverses the direction of TCP-style connections. One
  program connects to another over a secure WebSocket, and that program then opens connections back through the
  WebSocket, as if it could connect directly."
- It carries reliable, ordered byte streams only, like TCP. It has no datagrams.
- It mentions no protocol that runs over it, and depends on no gRPC library. gRPC is only its main use.
- Many connections share one WebSocket, multiplexed with yamux (`github.com/hashicorp/yamux`). yamux is an
  implementation detail: nothing in tenet's API or documentation names it.

### Transport
- The outer connection is a secure WebSocket only. The server serves it itself, or behind an HTTPS proxy that
  terminates TLS with its own certificate, such as the edge of a hosting platform that accepts only HTTPS. Raw TLS and
  SSH are not used: a WebSocket covers every deployment that they would, and it passes through the HTTP proxies of
  networks that allow only outbound connections.

- The WebSocket names a versioned subprotocol, such as `tenet.v1`, in its `Sec-WebSocket-Protocol` header. `Connect`
  sends it, and `Accept` confirms it or refuses the upgrade, so that a later change to the wire format is negotiated
  instead of breaking older peers. Only tenet's own code takes part, so whatever serves a `Listener` never sees it.

### The client's side
- `Connect` returns a `Client`, which keeps a tunnel open to the server. `Client.Listen` returns a `net.Listener`
  for each network and address. Any protocol's server that accepts connections can serve it, such as
  `grpc.Server.Serve`.
- It connects with an `http.Client` and request headers that its application gives it, so redirects, proxies and TLS
  follow that client, as for any other HTTP request. tenet adds no rules of its own.
- It connects again whenever its WebSocket ends, with a backoff policy that its application chooses.
- It tells its application each time a tunnel opens, ends or fails to open, through an observer.

### The server's side
- The server admits each client in its own HTTP handler, with whatever checks it uses for other requests, such as a
  token, basic auth, or mutual TLS where it terminates TLS itself. The handler then passes the request to tenet's
  `Accept`, which upgrades it and returns a `Dialer`, the server's half of the tunnel, in the same function. The
  `Dialer` doesn't depend on the request's context, so it lives on after the handler returns.
- The `Dialer`'s `DialContext(ctx, network, address)` opens a new `net.Conn` to the client's `Listener` for that
  network and address, over the same WebSocket. With gRPC, it is passed to `grpc.WithContextDialer`, and grpc-go's own
  reconnects and retries work as designed while the WebSocket lives.
- The `Dialer`'s `Done()` signals that the WebSocket has ended, and its `Close()` ends it.

### Liveness and bounds
- Each end has two settings, both about liveness: an interval, which is how often it checks that the other end still
  answers, and a timeout, which is how long a check or a write may stall before the tunnel ends. They play the part of
  TCP keepalive, so a silent break ends the WebSocket on whichever end notices first.
- Everything else is fixed and documented as bounds, as the kernel's settings are for TCP: at most 256 connections
  waiting for a `Listener` to accept them, and at most 256 KB buffered per connection in each direction. A connection
  beyond the backlog is reset, as TCP resets one beyond its own backlog.

### Limits
- tenet adds no limits on connections, and no timeout on dialing one. A `Listener` limits what it accepts, and the
  `Dialer` what it dials, as they would without a tunnel.
- A dead client is noticed by the liveness check, and a `Listener` that stops accepting leaves the `Dialer` to its own
  context and deadlines, as a TCP backlog does.
- `DialContext` returns as soon as its context ends, and a cancelled dial leaves nothing waiting behind it, so a
  `Dialer` that keeps retrying against a `Listener` that never accepts can't pile up work inside the tunnel.

### Ending
- Closing a `Listener` stops only its network and address: later dials to it fail, and existing connections are left to
  the application. Closing the `Client` stops it from connecting again and closes each `Listener`, and the WebSocket
  ends after the last connection closes. Grace and its deadline come from the protocol's server on top, such as
  `grpc.Server.GracefulStop`.
- Closing the `Dialer` ends the WebSocket and every connection immediately.
- When a WebSocket ends, every connection on it ends, pending dials fail, and later dials fail.
- Why a tunnel ended is reported as an error on both sides: from the server's `Dialer`, and to the client's observer,
  which is also told why an attempt to connect failed. `Listener.Accept` doesn't report it, because the `Listener`
  outlives each WebSocket, and an error from `Accept` would stop the protocol's server that serves it. tenet doesn't
  log, just as Go's `net` package doesn't.

### Identity
- tenet doesn't know who connected, or which WebSocket replaces which. Each server works that out from what it learns
  over the connections, such as the certificate that the protocol's server presents, or what that server reports about
  itself.

  examples, delivered as [its own plan](2026-11-17-tenet-v1-api.md) says.
- [ ] **Both sides, in Go**: the client's `Client` and `Listener`, and the server's `Dialer`. Their tests run each end
  against the other, and cover: two connections with one stalled, a dial cancelled while it is blocked, connections
  closed and dialed again repeatedly on one WebSocket, a silent loss of the network noticed by each end, shutdown
  during concurrent dials, a full backlog, and abrupt close by either end.

## Open
