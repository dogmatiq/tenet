# tenet v1: public API

## Context

This is a sub-plan of the [tenet v1 plan](2026-11-17-tenet-v1.md). It writes tenet's exported API as Go declarations
with their doc comments, so that the API can be reviewed as `go doc` shows it before anything is built behind it. Each
exported function and method has the body `panic("not implemented")`, and the exported types have no fields yet. Nothing
unexported is written, and there are no tests, only examples that are compiled but not run. The parent plan's tasks from
Tunnel to Liveness implement and test this API.

## Decisions

### The server's side
- `func Accept(w http.ResponseWriter, r *http.Request, options ...AcceptOption) (*Dialer, error)`. The server's handler
  calls it after it has admitted the client. If the upgrade to a WebSocket fails, Accept has already written an HTTP
  error response to `w`, and returns an error. The `*Dialer` doesn't depend on `r.Context()`, so it lives on after the
  handler returns.
- `Dialer`'s doc comment: "A Dialer is the server's half of a tunnel to a Client." Each tunnel gets its own
  `*Dialer`, so when the client connects again, `Accept` returns a new one.
- `func (d *Dialer) DialContext(ctx context.Context, network, address string) (net.Conn, error)` opens a connection to
  the client's `Listener` for exactly that network and address. If the client has no such `Listener`, it returns an
  error that wraps `syscall.ECONNREFUSED`. It returns an error that wraps `ctx.Err()` as soon as `ctx` ends, and leaves
  nothing waiting in the tunnel, and an error that wraps `d.Err()` once the tunnel has ended.
- `func (d *Dialer) Done() <-chan struct{}` returns a channel that is closed when the WebSocket ends.
- `func (d *Dialer) Err() error` returns nil until the channel from Done is closed, and then why the WebSocket ended. It
  returns `net.ErrClosed` if `d.Close` ended it.
- `func (d *Dialer) Close() error` ends the WebSocket and every connection on it. It may be called more than once, and
  returns nil; it returns an error only so that `*Dialer` is an `io.Closer`.

### The client's side
- `func Connect(url string, options ...ConnectOption) (*Client, error)` returns immediately, and connects to the
  WebSocket server at `url` in the background, and again whenever the WebSocket ends. It returns an error only if `url`
  doesn't parse or its scheme isn't `ws` or `wss`. The HTTP client and the header that it connects with are options,
  under Configuration. The Addresses section says why it takes no `ctx`, and what `Client` is.
- `Listener`'s doc comment: "A Listener is a net.Listener for the connections that the server opens with
  Dialer.DialContext for one network and address." `Client.Listen` returns one, and it may be used until
  `Listener.Close` or `Client.Close` is called.
- `func (l *Listener) Accept() (net.Conn, error)` waits for the next connection that the server opens to its network
  and address, across tunnels. It returns `net.ErrClosed` after `Listener.Close` or `Client.Close`. It reports no other
  error, so a tunnel that ends doesn't stop a function such as `http.Server.Serve` that is serving the `Listener`. Why
  each tunnel ended, or why an attempt to connect failed, goes to the `ClientObserver`.
- `func (l *Listener) Close() error` stops only this `Listener`. Connections that the server has opened but `Accept`
  hasn't returned are closed, as a TCP listener's backlog is. Connections that `Accept` has returned are left to the
  application. Afterwards a dial to its network and address returns an error that wraps `syscall.ECONNREFUSED`, and
  `Client.Listen` may be called again for that pair. It returns nil.
- `func (l *Listener) Addr() net.Addr` returns an address with the network and address given to `Client.Listen`.

### What the doc comments promise about connections and addresses
- The connections that `Dialer.DialContext` and `Listener.Accept` return are `net.Conn` values, with deadlines as
  `net.Conn` requires. The doc comments promise nothing more about them, such as half-close.
- Each connection's address at the `Listener`'s end, which is `LocalAddr` at the client and `RemoteAddr` at the
  server, returns the network and address given to `Client.Listen` and `Dialer.DialContext`, as TCP does.
  `Listener.Addr` returns the same. At the server, `LocalAddr` has the same network, and an empty string as its
  address, as the unnamed end of a Unix socket connection does. At the client, `RemoteAddr` likewise has the
  `Listener`'s network and an empty string as its address.

### Package documentation
- The package doc is the README's opening sentences, and nothing more. The README's Concepts section defines the terms,
  and the README says how a tunnel works and states the fixed bounds, and the examples in `example_test.go` show each
  end's use, without naming a protocol that runs over it. Prose belongs in the README and examples in testable examples.
- The bounds, 256 connections waiting for a `Listener` and 256 KB per connection in each direction, are stated in the
  README, not as exported constants, so that no code depends on them.

### Terms
- "Client" and "server" mean only the two ends of the WebSocket, which are tenet's own roles. The doc comments use
  these terms, which the README's Concepts section defines:
  - The **client** calls `Connect`. It makes the HTTP request that becomes the WebSocket, and accepts connections
    from its `Listener` values.
  - The **server**'s `http.Handler` calls `Accept`. It opens connections with the `Dialer`.
  - A **tunnel** is the WebSocket between them. Connections pass through it.
  - A **connection** is each stream through a tunnel. Its two ends are named by the types that hold them: the
    `Dialer`'s end and the `Listener`'s end.
- tenet doesn't name the roles inside a connection, which belong to the protocol that runs over it. A server for such
  a protocol is always named with that protocol, such as `grpc.Server`.
- The doc comments don't name the package in prose, such as "a version of tenet". The string `"tenet"` that
  addresses return as their network is a value, so the docs quote it.
- The README's Concepts section defines the terms. Each function's and type's doc says how it is meant to be used, what
  happens, what it returns, and how long the result may be used, without defining terms or naming the program's role.
  Using a term is not an explanation.
- A type's doc says what the type is, how to get one, and how long it may be used. What a method does belongs in that
  method's doc.
- The README's opening paragraph says "program", so that it needs none of these terms.

### Addresses
- Each connection carries an address, which the server gives when it opens the connection, so that
  one tunnel can reach several destinations, as one machine serves many TCP ports. tenet treats the address as an
  opaque string. It is in v1, because the wire format has to carry it from the start.
- `Dialer` matches `net.Dialer`: `Dial(ctx)` becomes `DialContext(ctx context.Context, network, address string)
  (net.Conn, error)`, so `Dialer.DialContext` can be passed to `http.Transport.DialContext` as it is.
- The client listens on each address separately, as `net.Listen` does. A new type owns the WebSocket and its
  reconnects, and its `Listen(network, address string) (*Listener, error)` method returns a `Listener` for that
  network and address. `Listen` and its options become that type's constructor, and `Listener.Close` stops only its
  own address. A dial is routed by its network and address together, and a dial to a pair that nobody listens on
  returns a `*net.OpError` that wraps `syscall.ECONNREFUSED`, like a refused TCP dial. `Client.Listen` for a pair
  that already has an open `Listener` returns an error that wraps `syscall.EADDRINUSE`, like a TCP listen on a port in
  use. Each protocol's server, such as
  a gRPC server and an HTTP server, serves its own `Listener`, with no routing code of its own.
- The new type is `Client`, the README's term for the role that it plays. `Connect(url string, options
  ...ConnectOption) (*Client, error)` makes one, and `ConnectOption` replaces `ListenOption`. There is no `Server`
  type, because the server keeps nothing between tunnels: each call to `Accept` returns a `Dialer` for one tunnel.
- `Connect` returns immediately and connects in the background, so it takes no `ctx`: in Go a `ctx` bounds the call
  that takes it, and `Connect` has nothing to wait for. `Client.Close` is the only way to stop a `Client`. It lets open
  connections finish, so stopping immediately means closing them, as `grpc.Server.Stop` does. This replaces the
  `ctx` that `Listen` took.
- A `ClientObserver` interface, given to `Connect` by `WithClientObserver`, tells the application about its tunnels
  through three methods: `TunnelOpened()`, `TunnelEnded(err error)` and `TunnelFailed(err error)`. The methods keep
  the `Tunnel` prefix, because the application implements them on its own type, where the interface's name isn't next
  to them. Each `TunnelOpened` call is matched by exactly one `TunnelEnded` call, and an attempt to connect that fails
  gets only a `TunnelFailed` call. `TunnelEnded` gets an error that wraps `net.ErrClosed`, never nil, if `Client.Close`
  ended the tunnel, as `Dialer.Err` does after `Dialer.Close`. The methods take no information about the `Client`:
  an application that supervises many gives each its own observer that points to its own record, because the first
  call can come before `Connect` returns, and two clients can share a URL. The observer must be safe for concurrent
  use if it is shared, because the calls for different clients may overlap.

### Configuration
- Settings are functional options, and each has a default that its doc states.
- `AcceptOption` is an option that `Accept` takes, and `ConnectOption` is one that `Connect` takes. `Option` embeds
  both, for the options that both take, so passing a `Connect`-only option to `Accept` doesn't compile. Their methods
  are unexported, so only tenet makes options. If the same option is given more than once, the last one applies.
- `WithKeepAliveInterval(d time.Duration) Option` sets how often each end of the WebSocket checks that the other end
  still answers. The default is 15 seconds.
- `WithKeepAliveTimeout(d time.Duration) Option` sets how long a check, or a write to the WebSocket, may stall before
  the WebSocket ends. The default is 10 seconds.
- `WithKeepAliveInterval` is named after `net.KeepAliveConfig.Interval`. Go has no TCP setting for the timeout, so
  `WithKeepAliveTimeout` only shares the prefix.
- `WithBackoff(f func(n int, err error) time.Duration) ConnectOption` sets the `Client`'s backoff policy, which decides
  how long it waits before it connects again. The policy is a function that the `Client` calls each time the WebSocket
  ends, and each time an attempt to connect fails, with why in `err`. `n` counts the calls since a WebSocket was last
  established, starting at 1. The default waits 1 second, doubles the wait after each call up to 1 minute, and adds
  random jitter to each wait.
- `WithHTTPClient(c *http.Client) ConnectOption` sets the client that makes each attempt to connect. The default is
  `http.DefaultClient`.
- `WithHeader(h http.Header) ConnectOption` sets the headers that each attempt to connect sends. `WithHeader` copies it.
  These are in addition to the headers that the `http.Client` and the upgrade to a WebSocket add.
- Each option panics if its argument is a non-positive duration, or a nil function, client or observer.

## Delivery order

Tick each item when it is done, and write the pull request or commit that did it beside it.

- [x] **Entry points** (270db9b): the exported declarations and doc comments for both sides, with
  `panic("not implemented")` bodies. `doc.go` holds the package documentation. `accept.go` holds `Accept`, and `Dialer`
  with `Dial`, `Done`, `Err` and `Close`. `listen.go` holds `Listen`, and `Listener` with `Accept`, `Close` and `Addr`.
  The liveness settings and the backoff are left out of the signatures until the next task.
- [x] **`Dialer`** (c043892): `Accept`, and `Dialer` with `DialContext`, `Done`, `Err` and `Close`, in `dialer.go`,
  which replaces `accept.go`, as the Decisions say, in the terms of the README. `Accept` takes no options until
  the option types task.
- [x] **`Client`** (c765152): `Connect`, and `Client` with `Listen` and `Close`, in `client.go`. The `Listen` function
  is removed. `Connect` takes `options ...ConnectOption`, and `ConnectOption` and `WithHTTPClient` are added in
  `options.go`, so that the HTTP client is configurable from the start. `ClientObserver`, in `clientobserver.go`, and
  `WithClientObserver`, in `options.go`, are added for the same reason.
- [x] **`Listener`** (83bca63): `Listener` with `Accept`, `Close` and `Addr`, in `listener.go`, which replaces
  `listen.go`, for one network and address.
- [x] **Option types** (eac6831): `AcceptOption` and `Option`, in `options.go`, and the `options` parameter of `Accept`.
- [x] **Options** (6e9a575): `WithKeepAliveInterval`, `WithKeepAliveTimeout`, `WithBackoff` and `WithHeader`, in
  `options.go`, as Configuration under Decisions says.
- [x] **Package doc** (6a7eaae): `doc.go`, which is the README's opening sentences. The README also says how a tunnel
  works and states the bounds, and `example_test.go` has an example for `Connect` and one for `Accept`.

Each task is one type, or one small group of declarations, so that each review is small.

Each task ends with `go build ./...` and `go vet ./...` passing, and `go doc -all .` read through as a user would.
