# tenet v1: public API

## Context

This is a sub-plan of the [tenet v1 plan](2026-11-17-tenet-v1.md). It writes tenet's exported API as Go declarations
with their doc comments, so that the API can be reviewed as `go doc` shows it before anything is built behind it. Each
exported function and method has the body `panic("not implemented")`, and the exported types have no fields yet.
Nothing unexported is written, and there are no tests. The parent plan's **Both sides, in Go** task implements and
tests this API.

The Decisions below were written with the parent plan's terms. The doc comments use the terms under Terms instead.

The main entry points come first. Configuration, that is the liveness settings and the backoff, comes in a second
task, once the entry points are approved.

It needs the parent plan's Setup task first, because `doc.go` and `go.mod` still hold the template's placeholders.

## Decisions

### The acceptor's side
- `func Accept(w http.ResponseWriter, r *http.Request) (*Dialer, error)`. The acceptor's handler calls it after it has
  admitted the initiator. If the upgrade to a WebSocket fails, Accept has already written an HTTP error response to `w`,
  and returns an error. The `*Dialer` doesn't depend on `r.Context()`, so it lives on after the handler returns.
- `Dialer`'s doc comment: "A Dialer dials connections to an initiator's listener through one WebSocket." Each
  WebSocket gets its own `*Dialer`, so when an initiator connects again, Accept returns a new one.
- `func (d *Dialer) Dial(ctx context.Context) (net.Conn, error)` opens a new connection to the listener. It has no
  network or address, because there is only one listener to reach. It returns an error that wraps `ctx.Err()` as soon
  as `ctx` ends, an error that wraps `d.Err()` once the WebSocket has ended, and an error immediately if the listener is
  closed.
- `func (d *Dialer) Done() <-chan struct{}` returns a channel that is closed when the WebSocket ends.
- `func (d *Dialer) Err() error` returns nil until the channel from Done is closed, and then why the WebSocket ended. It
  returns `net.ErrClosed` if `d.Close` ended it.
- `func (d *Dialer) Close() error` ends the WebSocket and every connection on it. It may be called more than once, and
  returns nil; it returns an error only so that `*Dialer` is an `io.Closer`.

### The initiator's side
- `func Listen(ctx context.Context, url string, options ...ListenOption) (*Listener, error)` returns immediately, and
  connects to the WebSocket server at `url` in the background, and again whenever the WebSocket ends. It returns an
  error only if `url` doesn't parse or its scheme isn't `ws` or `wss`. The HTTP client and the header that it connects
  with are options, under Configuration.
- `ctx` lives as long as the listener. Cancelling it ends the WebSocket and every connection immediately, and stops the
  listener connecting again.
- `Listener`'s doc comment: "A Listener accepts the connections that an acceptor dials through the WebSocket that
  Listen connects." `*Listener` implements `net.Listener`.
- `func (l *Listener) Accept() (net.Conn, error)` waits for the next connection that the acceptor dials, across
  WebSockets. It returns `net.ErrClosed` after `l.Close`, and an error that wraps `ctx.Err()` once `ctx` is cancelled.
  It reports no other error, so a WebSocket that ends doesn't stop a server that is serving the listener. Why each
  WebSocket ended, or why an attempt to connect failed, goes to the backoff function, in the configuration task.
- `func (l *Listener) Close() error` stops the listener connecting again. No new connections open, the dialer's new
  dials fail immediately, existing connections are left to the application, and the WebSocket ends after the last one
  closes. It returns nil.
- `func (l *Listener) Addr() net.Addr` returns an address whose `Network` method returns `"tenet"`.

### What the doc comments promise about connections and addresses
- The connections that `Dial` and `Accept` return are `net.Conn` values, with deadlines as `net.Conn` requires. The doc
  comments promise nothing more about them, such as half-close.
- Each connection's address at the `Listener`'s end, which is `LocalAddr` at the client and `RemoteAddr` at the
  server, returns the network and address given to `Client.Listen` and `Dialer.DialContext`, as TCP does.
  `Listener.Addr` returns the same. At the server, `LocalAddr` has the same network, and an empty string as its
  address, as the unnamed end of a Unix socket connection does. What `RemoteAddr` returns at the client is decided in
  the `Listener` task.

### Package documentation
- It starts with the README's first sentence, defines the parent plan's terms, states the fixed bounds, says that tenet
  doesn't log, and sketches each side's use without naming a protocol that runs over tenet.
- The bounds, 256 connections waiting for the listener and 256 KB per connection in each direction, are stated there,
  not as exported constants, so that no code depends on them.

### Terms
- "Client" and "server" mean only the two ends of the WebSocket, which are tenet's own roles. The doc comments use
  these terms, which the package doc defines:
  - The **client** calls `Connect`. It makes the HTTP request that becomes the WebSocket, and accepts connections
    from its `Listener` values.
  - The **server**'s `http.Handler` calls `Accept`. It opens connections with the `Dialer`.
  - A **tunnel** is one WebSocket between them, and the connections through it.
  - A **connection** is each stream through a tunnel. Its two ends are named by the types that hold them: the
    `Dialer`'s end and the `Listener`'s end.
- tenet doesn't name the roles inside a connection, which belong to the protocol that runs over it. A server for such
  a protocol is always named with that protocol, such as `grpc.Server`, and the package doc says once that such a
  server usually runs in the tenet client.
- The doc comments don't name the package in prose, such as "a version of tenet". The string `"tenet"` that
  addresses return as their network is a value, so the docs quote it.
- The package doc defines the terms. Each function's and type's doc says how it is meant to be used, what happens,
  what it returns, and how long the result may be used, without defining terms or naming the program's role. Using a
  term is not an explanation.
- A type's doc says what the type is, how to get one, and how long it may be used. What a method does belongs in that
  method's doc.
- The README's first sentence says "a program" and "another program", so that it needs none of these terms.

### Addresses
- Each connection carries an address, which the server gives when it opens the connection, so that
  one tunnel can reach several destinations, as one machine serves many TCP ports. tenet treats the address as an
  opaque string. It is in v1, because the wire format has to carry it from the start.
- `Dialer` matches `net.Dialer`: `Dial(ctx)` becomes `DialContext(ctx context.Context, network, address string)
  (net.Conn, error)`, so `Dialer.DialContext` can be passed to `http.Transport.DialContext` as it is.
- The client listens on each address separately, as `net.Listen` does. A new type owns the WebSocket and its
  reconnects, and its `Listen(network, address string) (*Listener, error)` method returns a `Listener` for that
  network and address. `Listen` and its options become that type's constructor, and `Listener.Close` stops only its
  own address. A dial is routed by its network and address together, and a dial to a pair that nobody listens on
  returns a `*net.OpError` that wraps `syscall.ECONNREFUSED`, like a refused TCP dial. Each protocol's server, such as
  a gRPC server and an HTTP server, serves its own `Listener`, with no routing code of its own.
- The new type is `Client`, the package doc's term for the role that it plays. `Connect(ctx context.Context, url
  string, options ...ConnectOption) (*Client, error)` makes one, and `ConnectOption` replaces `ListenOption`. There is
  no `Server` type, because the server keeps nothing between tunnels: each call to `Accept` returns a `Dialer` for one
  tunnel.

### Configuration
- Settings are functional options, and each has a default that its doc states.
- `AcceptOption` is an option that `Accept` takes, and `ListenOption` is one that `Listen` takes. `Option` embeds both,
  for the options that both take, so passing a `Listen`-only option to `Accept` doesn't compile. Their methods are
  unexported, so only tenet makes options. If the same option is given more than once, the last one applies.
- `WithKeepAliveInterval(d time.Duration) Option` sets how often each end of the WebSocket checks that the other end
  still answers. The default is 15 seconds.
- `WithKeepAliveTimeout(d time.Duration) Option` sets how long a check, or a write to the WebSocket, may stall before
  the WebSocket ends. The default is 10 seconds.
- `WithKeepAliveInterval` is named after `net.KeepAliveConfig.Interval`. Go has no TCP setting for the timeout, so
  `WithKeepAliveTimeout` only shares the prefix.
- `WithBackoff(f func(n int, err error) time.Duration) ListenOption` sets the function that says how long a `Listener`
  waits before it connects again. The `Listener` calls it each time the WebSocket ends, and each time an attempt to
  connect fails, with why in `err`. `n` counts the calls since a WebSocket was last established, starting at 1. The
  default waits 1 second, doubles the wait after each call up to 1 minute, and adds random jitter to each wait.
- `WithHTTPClient(c *http.Client) ListenOption` sets the client that makes each attempt to connect. The default is
  `http.DefaultClient`.
- `WithHeader(h http.Header) ListenOption` sets the header that each attempt to connect sends. `Listen` sends a copy of
  it. The default is no header.
- Each option panics if its argument is a non-positive duration, or a nil function or client.

Tick each item when it is done, and write the pull request or commit that did it beside it.

  `panic("not implemented")` bodies. `doc.go` holds the package documentation. `accept.go` holds `Accept`, and `Dialer`
  with `Dial`, `Done`, `Err` and `Close`. `listen.go` holds `Listen`, and `Listener` with `Accept`, `Close` and `Addr`.
  The liveness settings and the backoff are left out of the signatures until the next task.

  option types task.
- [ ] **`Client`**: `Connect`, and `Client` with `Listen` and `Close`, in `client.go`. The `Listen` function is
  removed. `Connect` takes the server's URL only, until the option types task.
- [ ] **`Listener`**: `Listener` with `Accept`, `Close` and `Addr`, in `listener.go`, which replaces `listen.go`, for
  one network and address.
- [ ] **Option types**: `AcceptOption`, `ConnectOption` and `Option`, in `options.go`, and the `options` parameters of
  `Accept` and `Connect`.
- [ ] **Options**: `WithKeepAliveInterval`, `WithKeepAliveTimeout`, `WithBackoff`, `WithHTTPClient` and `WithHeader`,
  in `options.go`, as Configuration under Decisions says.
- [ ] **Package doc**: `doc.go`, with the terms, how a tunnel works, its use and its bounds, and the README's first
  sentence to match.

Each task is one type, or one small group of declarations, so that each review is small. Earlier drafts of all of them
are in the stash "tenet API drafts: configuration, terms, docs", for reference only.

Each task ends with `go build ./...` and `go vet ./...` passing, and `go doc -all .` read through as a user would.
